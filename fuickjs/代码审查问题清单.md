# FuickJS 核心渲染路径 — 问题清单

> 审查范围：JS 框架层（`fuickjs_framework/fuickjs/`）、Flutter 框架层（`fuickjs_framework/fuickjs_flutter/`）、Taro 适配层（`taro-fuickjs/`）
> 审查维度：代码质量、性能、内存、可维护性

按严重程度分级，每条含位置、现象、证据与建议。

---

## P0 — 明确缺陷 / 零风险，应立即修复

### 1. 生产日志污染（绕过日志门控）

| 项 | 内容 |
|----|------|
| **位置** | `ListItemManager.ts:96,144,170`、`websocket.ts`(7 处)、`NavigatorService.ts:55,95`、`page_render.ts:187,216` |
| **现象** | 高频路径用裸 `console.log`，绕过了框架已有的 `perfLog` 调试开关 |
| **证据** | `utils/log.ts:5-13` 已实现 `setDebug()/perfLog()` 门控，但这些位置直接 `console.log`。`stateful` 列表滚动时每个 item 创建/销毁打 3 条，长列表滚动刷屏 |
| **建议** | 统一收敛到 `perfLog`，或引入 `logLevel` 分级，生产默认静默 |
| **状态** | 已修复。`utils/log.ts` 新增 `logDebug()`，与 `perfLog()` 共用 `setDebug()` 门控；上述 12 处 `console.log` 全部替换（`[Perf]` 埋点走 `perfLog`，其余走 `logDebug`）。`console.warn/error` 保持不变 |

### 2. Flutter 侧节点表潜在泄漏（patchUI 路径）

| 项 | 内容 |
|----|------|
| **位置** | `fuickjs_flutter/lib/core/widgets/fuick_node.dart:185-193`（`applyPatches`） |
| **现象** | `applyPatches` 只 `createNode`，从不清理不再出现的孤儿节点 |
| **证据** | 清理逻辑仅存在于 `applyOps` 的 DELETE 分支（`_disposeSubtree`，第 250 行）。当 `incrementalMode=false` 走 `DiffStrategy → patchUI` 时，条件渲染移除的子树、列表减少的节点 id 永久残留在 `_nodes` 表 |
| **建议** | `applyPatches` 后做孤儿回收，或统一 GC 不被根可达的节点 |
| **状态** | 待处理。核实后范围比原判断更大：全量 `renderUI` 路径（`fuick_page_view.dart:_handleRenderDsl` → 从根 `createNode`）同样不回收孤儿，而 `DiffStrategy` 只要根节点变化就走全量 `renderUI`，故 diff 模式下两条路径都在漏。修法上 per-parent 增量回收会误删被搬移复用的同 id 节点，需要给 `FuickNodeManager` 加根引用后做 mark-and-sweep，建议先写复现用例 |

## P1 — 一致性与健壮性问题

### 3. 透明节点 type 判定不一致 + 死代码

| 项 | 内容 |
|----|------|
| **位置** | JS 侧 `node.ts:90,219`、`PageContainer.ts:531`、`DiffStrategy.ts:71`、`IncrementalStrategy.ts` 多处；Dart 侧 `fuick_node.dart:67-70` |
| **现象** | `FlutterProps` 透明节点 type 字符串散落 7+ 处硬编码，且两侧判定不一致 |
| **证据** | Dart 侧多判了 `'Props'`（`fuick_node.dart:69`），但 JS 侧从不产出该值 → 死代码 |
| **建议** | 收敛为单一常量 `TRANSPARENT_TYPES`，删除 `'Props'` 死分支 |
| **状态** | 已修复。新增 `core/constants.ts`（`TRANSPARENT_TYPES` / `isTransparentType()` / `FLUTTER_PROPS_TYPE`），JS 侧 10 处硬编码 + 产出侧 `FlutterProps.tsx` 全部改为引用常量；Dart 侧新增 `kTransparentNodeTypes` 并删除 `'Props'` 分支 |

### 4. 手写 barrel 无对称性校验（已造成实际断链）

| 项 | 内容 |
|----|------|
| **位置** | `widgets/index.ts`(102 行 export) + `widget_factory.dart`(100 行 register) |
| **现象** | JS/Flutter 两侧注册表纯手写、无交叉校验，新增组件易漏改某一侧 |
| **证据** | Taro 侧 `<Video>` 已映射 `VideoPlayer`，但 Flutter 侧**没有** `VideoPlayerParser`，实际调用静默降级为 `SizedBox.shrink()` |
| **建议** | 用 build_runner + 构建脚本自动生成 barrel，或加 lint 校验两侧对称 |
| **状态** | 待处理。断链已核实：`components-fuickjs/src/Video.tsx:27` 渲染 `WidgetNames.VideoPlayer`，而 `fuickjs_flutter/lib` 全目录 grep `Video` 零命中。补充一点：并非完全静默，`widget_factory.dart:413` 会 `logger.w('Unknown widget type: ...')`，只是 UI 上什么都不渲染 |

## P2 — 性能与可维护性优化

### 5. 递归比较函数职责重叠

| 项 | 内容 |
|----|------|
| **位置** | `hostConfig.ts:6`（`deepEqual`）+ `hostConfig.ts:131`（`isDslEqual`） |
| **现象** | 两套近 40 行的递归深比较逻辑并存，唯一区别是"函数引用是否算不同" |
| **建议** | 合并为 `deepEqual(a, b, { treatFunctionsAsEqual })`，消除一半代码 |
| **状态** | 已修复。`isDslEqual` 删除，统一为 `deepEqual(a, b, options?)`。合并后行为有一处变严：原 `deepEqual` 缺少数组/对象形状检查（`[1]` 与 `{0:1}` 判等），现统一沿用 `isDslEqual` 的 `Array.isArray` 检查 |

### 6. `FuickNode.getProp` 缓存整页失效

| 项 | 内容 |
|----|------|
| **位置** | `fuickjs_flutter/lib/core/widgets/fuick_node.dart:89-99` |
| **现象** | 任何 prop 变化触发 `_resolvedProps.clear()`，全部嵌套节点缓存失效 |
| **证据** | `AppBar.title`/`Scaffold.appBar` 等 Map 型 prop 会惰性 `createNode` 成节点树，一个无关 prop 变化就导致整树重新解析 |
| **建议** | 改为 per-key 失效（记录每个 key 的解析版本） |
| **状态** | 待处理。修正建议：应按 key 缓存"上次解析时的 raw 值引用"而非解析版本号。命中率由 raw prop 的对象身份决定——`applyOps` 走 `Map.from(node.props)` 合并，未变动的 Map 型 prop 保留原引用，per-key 能命中；而 `patchUI` / `renderUI` 重新解码 DSL，每个 Map 都是新实例，无论怎么分 key 都必然 miss |

### 7. `prepareUpdate` 已知妥协（提前 diff 缺失）

| 项 | 内容 |
|----|------|
| **位置** | `hostConfig.ts:321`（`prepareUpdate: () => true`） |
| **现象** | React 19 下返回值不再传给 `commitUpdate`，diff 全部推迟到 commit 阶段，每次 props 引用变化都触发全量 `diffProps` |
| **建议** | 属 React 19 兼容妥协，非 bug。升级 reconciler 到支持提前 diff 的版本后可省一整轮 diff + applyProps |
| **状态** | 不处理。受限于上游 reconciler，等依赖升级后再评估 |
